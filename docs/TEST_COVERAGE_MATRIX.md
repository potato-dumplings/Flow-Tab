## Purpose

This document gives a product-scenario view of FlowTab test coverage. It complements the existing layer-focused documents:

- [UNIT_AND_BEHAVIOR_TEST_COVERAGE.md](UNIT_AND_BEHAVIOR_TEST_COVERAGE.md)

Use this matrix when deciding whether a feature has enough automated evidence across unit, behavior/integration, and UI/end-to-end layers.

## Status Legend

- `Strong`: the layer has direct automated coverage for the scenario.
- `Partial`: the layer has related automated coverage, but it does not prove the full user-visible or runtime outcome.
- `Not relevant`: the layer does not naturally apply to this scenario.
- `Gap`: the scenario still needs coverage in this layer.

## Recent Validation Notes

- 2026-06-17 Phase 5: `LiveSwitcherModel` now stores and uses its runtime dependency as `runtimeProjectionService`, so Switcher internals and constructor injection describe projection reads, dirty signals, committed Search-index reads, freshness-barrier requests, termination cleanup, and verified-focus writeback as projection-runtime ownership rather than a surface snapshot service.
- 2026-06-17 Phase 5: Home projection-reader ownership no longer lives in a snapshot-named source file. `HomeRuntimeSnapshotService.swift` was renamed to `HomeRuntimeProjectionService.swift`, and the Home initial first-frame reader now exposes `initialAppSummaries` / `appSummaries` instead of `lightweightAppSummaries`; remaining lightweight wording is historical test naming, while current behavior proof uses projection-read counts and dirty/maintenance signals.
- 2026-06-17 Phase 5: Home surface runtime injection now uses projection wording (`homeRuntimeProjectionService`, `runtimeProjectionService`) and the Home no-window transient-rebuild check reads through the injected projection service instead of the global shared runtime instance. This keeps Home's surface boundary aligned with projection-read/dirty-signal ownership, now through the `RuntimeProjectionServing` contract.
- 2026-06-20 Phase 5: `FlowTabTests+HomeWindowActivation` no longer uses dead lightweight snapshot counters as Home reader proof. Home activation, Home summary/detail, initial summary, app-switcher-derived Home data, and missing-projection repair-signal cases now assert Home summary projection reads, app-switcher projection reads, current-app projection reads, and dirty/maintenance signals. This is behavior-test oracle cleanup only; production behavior, UI/E2E, pressure, and real-topology status are unchanged.
- 2026-06-17 Phase 5: Search stale committed-index reads now report `degradedStaleCommittedResult` and `committedIndexCoversCurrentGeneration=0` in the Search-facing diagnostic/log path. A stale committed index can still provide degraded results while requesting the bounded freshness barrier, but until that barrier commits a new generation it is explicitly not `committedGenerationResult` and is no longer named or logged as `latestCommittedResult`, `freshResult`, or `completeResult`.
- 2026-06-18 Phase 5: Search stale committed-index diagnostics now assert the barrier-not-committed path is not logged as `committedGenerationResult`, `latestCommittedResult`, `freshResult`, or `completeResult`; the current behavior remains degraded/stale committed result plus dirty/freshness metadata until a scoped repair commits a new generation.
- 2026-06-19 Phase 5: Search freshness documentation now treats successful barrier commit as the only gate into latest-result state. The current barrier-not-committed behavior is documented as `degradedStaleCommittedResult` / stale committed read with dirty/freshness metadata, matching the existing stale-index diagnostics rather than describing it as fresh, complete, or latest; the deferred-repair behavior test also asserts the barrier-requested read is not current-generation committed and carries the dirty metadata.
- 2026-06-19 Phase 5: same appID multi-PID termination is now covered at the app directory projection boundary. `testRuntimeReadModelStorePreservesRunningInstanceWhenSameBundleDifferentPIDTerminates` proves a known secondary PID termination prunes only that directory entry, keeps the grouped app and committed Search entry as degraded/stale with dirty metadata, no-ops a duplicate signal, and deletes the app only when the surviving PID terminates. `testRuntimeProjectionServicePrunesTerminatedPIDButKeepsSameAppDirectoryInstance` proves the shared service signal path preserves the surviving directory entry and stale committed Search result. This adds unit/behavior ownership evidence only; committed/staging Search UI proof, broader real topology UI/E2E, and pressure status remain unchanged.
- 2026-06-18 Phase 5: Search read result naming moved into `RuntimeSearchIndexRead`; store tests now assert missing/current/stale committed reads return the matching `missingCommittedIndex`, `committedGenerationResult`, or `degradedStaleCommittedResult` state, and `LiveSwitcherModel` diagnostics consume that runtime-owned result state instead of remapping readiness at the surface.
